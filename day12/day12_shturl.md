\## 二、核心概念



\### 1. 统一返回格式的意义



\-  所有接口返回相同的最外层结构：`{"code": ..., "msg": ..., "data": ...}`

\-  前端只需根据 `code` 字段判断成功或失败，无需逐个接口适配

\-  禁止在接口中直接 `return` 原始数据，所有返回值都通过 `success\_resp` / `fail\_resp` 包裹

\-  修改返回格式（如新增 `timestamp` 字段）只需改工具函数，全局生效



\### 2. 全局异常处理器



\-  使用 `@app.exception\_handler(ExceptionType)` 注册

\-  参数校验异常（`RequestValidationError`）：提取 Pydantic 校验错误信息，格式化为友好提示

\-  业务异常（`BizException`）：携带自定义错误码和消息，由业务代码主动抛出

\-  未知异常（`Exception`）：兜底捕获所有未处理的错误，统一返回 500，避免暴露内部细节

\-  异常处理器的注册顺序：先注册最具体的异常类型，最后注册 `Exception` 兜底



\### 3. 自定义业务异常类



\-  继承 `Exception`，额外携带 `code` 和 `msg` 属性

\-  业务代码中遇到业务逻辑错误时，直接 `raise BizException("账号已存在", code=4001)`

\-  由全局异常处理器统一捕获并转换为标准错误响应



\### 4. HTTP 状态码 vs 业务状态码



\-  本次实践采用 HTTP 200 + 业务错误码方案

\-  好处：前端可以正常解析响应体，根据 `code` 判断业务结果

\-  参数校验失败：`code=422`；业务错误：自定义码如 `4001`；服务器错误：`code=500`



\### 5. 客户端参数来源总结



| 参数类型 | 在 URL 中的位置 | 接口示例 |

|----------|----------------|----------|

| 路径参数 | 路径的一部分 | `/student/{stu\_id}` |

| 查询参数 | `?` 后面 | `/user/info?username=zhangsan` |

| 请求体参数 | HTTP Body（正文） | `POST /user/register` 的 JSON |



\## 三、踩坑记录



1\.  \*\*异常处理器注册顺序\*\*：`BizException` 继承自 `Exception`，必须注册在 `Exception` 处理器之前，否则会被兜底处理器捕获，失去自定义错误码的功能。

2\.  \*\*`RequestValidationError` 错误信息提取\*\*：`exc.errors()` 返回列表，通常取第一个错误即可。需注意字段名和错误消息的拼接，确保返回给前端的信息清晰可读。

3\.  \*\*拼写细节\*\*：`unknow` 应写为 `unknown`；请求体模型命名建议统一为 `XxxReq`（Request），避免与响应模型混淆。

4\.  \*\*`async` 关键字\*\*：FastAPI 全局异常处理器要求使用 `async def`，即使函数体内没有异步操作也必须加，否则框架会报错。



\## 四、今日收获



1\.  全局异常处理让业务代码更简洁，不再需要到处写 `try-except`

2\.  统一返回格式是前后端协作的基础，极大降低沟通成本

3\.  通过自定义异常实现了业务错误与系统错误的清晰分离

4\.  异常处理器集中管理，便于后续扩展（如添加日志记录、告警通知）

5\.  理解了客户端如何构造 URL 和请求体，对 HTTP 交互有了更立体的认识
